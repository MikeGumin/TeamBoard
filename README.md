# TeamBoard 📋

Мини-Jira для команды: **доска задач** + **база знаний (документация)** + **роли (админ/рабочий)**.

Стек: **чистый HTML / CSS / JS** (без сборки) + **Supabase** (авторизация, база данных, realtime).
Хостинг: **GitHub Pages** (фронтенд), вся «серверная» логика — в Supabase.

## 1. Что умеет

| | Админ (капитан 👑) | Рабочий |
|---|---|---|
| Вкладка **«Задачи»** | видит **все** задачи команды, фильтры по статусу и исполнителю | видит **только свои** задачи |
| Создание/распределение задач | ✅ | ❌ |
| Смена статуса своей задачи (`todo → in_progress → review`) | ✅ любой статус | ✅ только до «На проверке» |
| Закрытие задачи (`done` / `closed`) | ✅ | ❌ (запрещено даже на уровне БД) |
| Комментарии к задачам | ✅ | ✅ |
| Вкладка **«Документация»** | читает, создаёт, редактирует, удаляет статьи | только читает |
| Вкладка **«Админ»** | управление командой + пригласительные коды | не видна |

Дополнительно:

- Kanban-доска со статусами **todo / in_progress / review / done / closed** (по аналогии с Jira).
- У задачи: заголовок, описание (Markdown), исполнитель, срок (с подсветкой просрочек), комментарии.
- **Ссылки на статьи внутри задач**: в описании пишите `[[doc:12]]` или `[[doc:12|Название]]` — при открытии задачи это кликабельная ссылка, открывающая статью. Либо кнопка «Скопировать ссылку на статью» в редакторе даёт прямую ссылку вида `…/#doc-12`.
- **Живое обновление** (Realtime): доска меняется у всех без перезагрузки.
- Регистрация новичков **только по одноразовым пригласительным кодам** админа.

## 3. Пошаговая настройка Supabase

### Шаг 0. Создание проекта

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) (бесплатного тарифа хватит с запасом).
2. **New project** → придумайте название (например `teamboard`), задайте **пароль от базы данных** (запишите его!), регион — ближайший к вам (например Frankfurt).
3. Подождите ~1–2 минуты, пока проект создастся.

### Шаг 1. Взять URL и anon key

В левом меню: **Project Settings (шестерёнка) → API**. Скопируйте:

- **Project URL** — вида `https://abcdefgh.supabase.co`
- **anon public** key — длинная строка `eyJhbGciOi...`

> ⚠️ Ключ **`service_role`** не копируем и **никогда** не вставляем во фронтенд — он обходит все правила безопасности.

Откройте `js/config.js` и вставьте:

```js
window.APP_CONFIG = {
  SUPABASE_URL: "https://abcdefgh.supabase.co",
  SUPABASE_ANON_KEY: "eyJhbGciOi...",
};
```

### Шаг 2. Отключить подтверждение email (рекомендую для начала)

Левое меню: **Authentication → Providers → Email**.
Выключите тумблер **"Confirm email"** → **Save**.

Почему: иначе каждый новичок должен перейти по письму, а бесплатная почтовая служба Supabase отправляет письма в спам и лимитирована (~2–4 письма/час). Для внутренней команды проще входить сразу. Если хотите подтверждения — оставьте включённым, приложение корректно попросит проверить почту.

### Шаг 3. Выполнить SQL-скрипты

Левое меню: **SQL Editor → New query**. Создавайте запросы, вставляя содержимое файлов **строго в порядке**:

1. содержимое [`supabase/01_schema.sql`](supabase/01_schema.sql) → **Run**
2. содержимое [`supabase/02_rls.sql`](supabase/02_rls.sql) → **Run**
3. содержимое [`supabase/03_functions.sql`](supabase/03_functions.sql) → **Run**
4. содержимое [`supabase/04_realtime.sql`](supabase/04_realtime.sql) → **Run** (опционально, но рекомендую)

Каждый скрипт идемпотентен (`if not exists` / `drop ... if exists`) — можно перезапускать после правок.

Проверка: **Table Editor** слева — должны появиться таблицы `profiles`, `tasks`, `docs`, `task_comments`, `invite_codes`, `invite_redemptions`.

### Шаг 4. Первый вход = вы становитесь админом 🔑

Важнейшее правило логики (триггер `handle_new_user` в `01_schema.sql`):

> **Самый первый зарегистрированный пользователь автоматически получает роль `admin`. Все остальные — `worker`.**

Поэтому: **первым регистрируетесь ВЫ**, и только потом раздаёте коды команде.

Если ошибётесь — исправить всегда можно вручную: **SQL Editor**:

```sql
update public.profiles set role = 'admin' where id = '<uuid пользователя из Authentication→Users>';
```

### Шаг 5. Локальный запуск (проверка перед деплоем)

Открывать `index.html` двойным кликом (`file://`) **не стоит** — лучше поднимите мини-сервер:

```bash
cd папка-проекта
python3 -m http.server 8000        # или: npx serve .
# открыть http://localhost:8000
```

Зарегистрируйтесь как первый пользователь → проверьте вкладку «Админ», создание задач и статей.

## 4. Как устроена авторизация и роли

Вы сомневались между «скрытым паролем», регистрацией ребят и Telegram-входом. Вот схема, которую я реализовал — она решает все три проблемы без бэкенда:

### Схема «пригласительные коды»

1. Вы (админ) на вкладке **«Админ»** жмёте **«Сгенерировать код»** → появляется короткий код (например `7f3a9c2e`).
2. Отправляете код человеку в мессенджере (это и есть ваш «секретный пароль», но **персональный и одноразовый**).
3. Он открывает сайт → вкладка **«Регистрация»** → имя, email, пароль, код.
4. До создания аккаунта клиент вызывает SQL-функцию `consume_invite_code(code, email)` — она в базе проверяет код и **атомарно помечает его использованным** («сжигает»). Недействительный/уже сожжённый код → регистрация невозможна.
5. Supabase Auth создаёт пользователя; триггер сам делает ему профиль (`worker`, кроме самого первого — `admin`).

Почему это лучше «одного общего пароля»: общий пароль утечёт целиком и навсегда, а код — одноразовый, и вы видите, кто им воспользовался. Плюс вы контролируете список: без кода система закрыта наглухо.

### Почему email+пароль, а не Telegram

- **Telegram Login Widget** требует: (а) держать домен сайта в *BotFather → /setdomain*, то есть сайт уже должен быть задеплоен; (б) проверку `hash` через HMAC-SHA256 с токеном бота — секрет бота нельзя класть во фронт, поэтому потребовалась бы Edge-функция (микро-бэкенд на Supabase). Реализуемо, но сложнее.
- Telegram — это ещё и отдельный аккаунт-требование для каждого члена команды, и невозможность войти «просто с рабочего ноутбука».
- Рекомендация: **стартуем на email+код**, Telegram добавляем позже (см. раздел 8) — схема ролей и RLS от этого не изменится, изменится только способ входа.

### Где реально живут права (важно!)

Права обеспечиваются **не в JS, а в базе** — через Row Level Security (`02_rls.sql`):

- создать/редактировать/удалить задачу, создать/править статью, читать коды приглашений — **только `is_admin()`**;
- рабочий может обновлять только **свою** задачу, и триггер `guard_task_update` не даст ему поставить `done/closed` или переписать текст/исполнителя — даже если залезть в консоль браузера и дёргать API напрямую;
- таблица `invite_codes` для анонимных полностью закрыта — код проверяется только функцией `consume_invite_code` (неверный код просто возвращает `false`, а валидный «сгорает»).

Анонимный key, который лежит в `js/config.js`, безопасен именно потому, что без логина через него видно и можно сделать **только** то, что разрешили политики RLS.

## 5. Деплой на GitHub Pages

1. Запушьте репозиторий на GitHub (этот проект — готовая структура, `git push`).
2. **Settings → Pages → Build and deployment**: Source = **Deploy from a branch**, Branch = `main` / `/(root)`, **Save**.
3. Через минуту сайт доступен по `https://ВАШ-ЛОГИН.github.io/РЕПОЗИТОРИЙ/`.
4. Вернитесь в Supabase: **Authentication → URL Configuration → Site URL** — впишите адрес Pages (нужно для редиректов, если включите подтверждение email).
5. Раздача статики из корня работает «из коробки», т.к. `index.html` лежит в корне.

> Совет: файлы `supabase/*.sql` держите в репозитории как источник истины по схеме БД — при правках структуры сначала меняете файл, потом выполняете его в SQL Editor.

## 6. Как пользоваться после запуска

**Вы (капитан):**
1. Регистрируетесь первым → вы админ.
2. Вкладка «Админ» → генерируете коды → рассылаете команде.
3. Вкладка «Задачи» → форма сверху: заголовок, исполнитель, срок, описание. В описании ссылаетесь на статьи через `[[doc:ID]]` (ID виден рядом с заголовком статьи и в списке).
4. Когда исполнитель довел задачу до «На проверке» — открываете карточку, читаете комментарии, жмёте ✅ «Закрыть (готово)».
5. Вкладка «Документация» → «+ Статья» — пишете регламенты в Markdown.

**Рабочий:**
1. Получил код → регистрация → вход.
2. Видит «Мои задачи». Открыл карточку → «Взять в работу» → пишет вопросы в комментарии → когда готов → «Отправить на проверку».

## 7. Безопасность: что важно понимать

- **Никогда** не кладите `service_role` key в `config.js` и вообще в клиентский код.
- Пароли пользователей хранит Supabase Auth (bcrypt), в наших таблицах их нет.
- Markdown из базы рендерится через DOMPurify (защита от XSS через статьи/описания).
- Стойкость invite-кодов: 8 hex-символов (~4 млрд комбинаций) + функция возвращает только `true/false`; при желании добавьте rate-limit в **Authentication → Rate limits**.
- Скажите команде использовать разные пароли: anon key публичный, но он ничего не даёт без аккаунта.

## 8. Идеи на будущее (включая Telegram)

1. **Telegram-вход вторым шагом**: поднять Supabase **Edge Function** (Deno, бесплатно), которая принимает `initData` от Telegram WebApp/бота, проверяет подпись секретами бота и создаёт/находит пользователя (через service_role key — он остаётся на сервере). Текущая схема «код приглашения» тогда заменяется на «кто есть в телеграм-группе» — RLS и роли трогать не придётся.
2. Уведомления о новых задачах в Telegram-канал (через того же Edge Function + Bot API).
3. Drag&drop карточек между колонками kanban.
4. Приоритеты (blocker/major/minor), теги, вложения через Supabase Storage.
5. **Canvas-вкладка** (о которой вы писали) — рисование схемы спикеров: `tldraw` или свой `<canvas>` + сохранение PNG в Supabase Storage. Сознательно не делал: сначала стоит закрыть базовый workflow задач.
6. История статусов задачи (таблица `task_events`) — «лента активности» как в Jira.
